title: Readiness
description: Keep an interface inactive until its declared initial requirements are ready.
---

`Readiness` coordinates the initial preparation of a React subtree. Its children
remain mounted and visible while requirements are pending, but they cannot be
focused or operated. When every initial requirement is ready, the subtree
becomes interactive once and remains interactive.

```tsx
<Readiness>
  <Application />
</Readiness>
```

`Readiness` participates transparently in the surrounding layout. It does not
apply a Surface, color, loading indicator, opacity, or visibility to its
children.

## Registering work

Call `useRequirement()` from the component that owns the state being prepared.
It returns a stable, idempotent function that marks that requirement ready.

```tsx
function Workspace() {
  const ready = useRequirement("Loading workspace")

  useEffect(() => {
    loadWorkspace().then(workspace => {
      setWorkspace(workspace)
      ready()
    })
  }, [ready])

  return <WorkspaceView />
}
```

Calling `ready()` means that the component owns a complete state it can render.
That state may be the requested content or an error state; readiness does not
mean that the underlying operation succeeded.

For work whose pending lifetime already matches mounted React state, use the
declarative part. It renders nothing and completes its requirement when it
unmounts.

```tsx
<Readiness>
  {loading && <Readiness.Requirement message="Loading programs" />}
  <ProgramList />
</Readiness>
```

Requirements register with the nearest boundary at any descendant depth. A
nested `Readiness` boundary represents all of its internal work as one
requirement to its parent.

## Presenting pending work

Without a `fallback`, pending content remains visible but inactive. When a
presentation is needed, pass a `fallback` function. It receives the complete
requirement history and returns any React node. The returned node is outside
the inactive subtree, so it owns its own interaction, position, material, and
visual treatment.

```tsx
<Readiness fallback={requirements => (
  <LoadingSurface requirements={requirements} />
)}>
  <Application />
</Readiness>
```

The fallback may cover the application, render beside it, or appear elsewhere
through its own composition. `Readiness` does not position or style it.

Each requirement contains:

| Field | Meaning |
| --- | --- |
| `message` | Text supplied by the requirement, or the boundary message when omitted. |
| `createdAt` | The time the requirement registered with the boundary. |
| `readyAt` | The time it became ready, or `null` while it remains pending. |

## Reading the boundary

`useReadiness()` reads the nearest boundary. It returns `ready` and the same
requirement history supplied to `fallback`.

```tsx
function ReadinessSummary() {
  const { ready, requirements } = useReadiness()

  return <span>
    {ready ? "Ready" : `${requirements.length} initial requirements`}
  </span>
}
```

## Initial readiness only

After its first transition to ready, a boundary never disables the interface
again. Later data updates remain ordinary application state and do not restore
the initial readiness cycle.

## Selected props

| Prop | Default | Use |
| --- | --- | --- |
| `message` | `Loading…` | Supply text for requirements that omit their own message. |
| `fallback` | none | Render an optional representation of the pending requirements. |
