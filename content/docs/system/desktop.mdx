A Desktop is one graphical representation of the System. The System owns the
authoritative state of each Client Window; the Desktop owns the measurements,
pointer interaction, iframe, animation, and temporary presentation needed to
show it on one screen.

This separation allows the same Window state to be represented by more than
one Desktop without treating browser-local details as System truth. The Client
Endpoint's `window` handle addresses the authoritative state. Its Context's
`localWindow` handle addresses the representation owned by the current Desktop.
The Desktop provides the mechanism that links these two representations or
allows the local representation to remain detached.

## Desktop state

`desktop.viewport` exposes the current workspace size in CSS pixels and emits a
complete `{ size }` snapshot when it changes. `desktop.preferences` exposes the
effective theme and animation choice for this Desktop and publishes complete
replacements.

```ts
const { size } = await desktop.viewport.snapshot()
const preferences = await desktop.preferences.snapshot()

console.log(size.width, size.height, preferences.theme)
```

`desktop.connection()` returns the browser Connection carrying this Desktop.
It requires `desktopConnection` or the broader `connections` permission.

## Authoritative Window state

Every Client Endpoint has one permanent `window` handle. Its title, header,
geometry, minimized state, maximized state, front state, and layer belong to
the System. Reads return those authoritative values; mutations change them and
publish the matching Window event.

```ts
await context.window.setGeometry({
  position: { x: 120, y: 80 },
  size: { width: 900, height: 640 },
})

await context.window.maximize()
await context.window.changeHeader(false)
```

`move()` and `resize()` change one part of the geometry. `setGeometry()` commits
position and size together. Geometry accepts finite pixels and relative values
such as `"1/2"`, `"50%"`, and `"50% + 10"`.

Minimized and maximized are independent boolean facts. Presentation resolves
them in this order: minimized, maximized, geometry. A minimized Window is
hidden. Otherwise, a maximized Window fills the workspace. Otherwise, the
stored geometry is shown. Neither state destroys the geometry underneath it,
so restoring a Window needs no separate saved rectangle.

Calling `minimize()` or `maximize()` without an argument sets that state to
`true`. `changeHeader()` controls whether a standard Window presents the
Desktop-owned top region containing its title, drag area, and controls. Hiding
it gives Client content the complete inner Window area without changing the
Window's layer, Surface, resize boundary, taskbar presence, or Desktop
authority. `raise()` makes the Window frontmost within its own layer.

## Layers

Windows occupy five isolated layers, ordered from back to front: `wallpaper`,
`under`, `window`, `over`, and `start-menu`. The taskbar remains above every
Window layer. Changing depth within one layer never crosses into another.

The `window` layer contains standard application windows. `under` and `over`
provide chrome-free presentation beneath and above standard windows while
retaining their own Surface behavior.

The `wallpaper` and `start-menu` layers are exclusive Desktop roles. Each can
contain one Client Endpoint. Starting another occupant in the same role ends
the existing occupant's entire Process before the replacement starts.

Desktop gives each role its fixed presentation. A `wallpaper` Client fills the
wallpaper area and replaces the Appearance wallpaper. A `start-menu` Client
fills the existing Start Menu area and replaces the built-in Start Menu. When
either Client stops, Desktop returns to that role's fallback.

Authoritative Window values remain readable and observable for both Clients,
but they do not determine either role's presentation.

## Local Window

`context.localWindow` controls only the representation on the current Desktop.
Its operations do not mutate authoritative Window state or emit Window events.

```ts
await context.localWindow
  .transaction({ duration: 180, easing: "ease-out", wait: true })
  .setGeometry({
    position: { x: 24, y: 24 },
    size: { width: 720, height: 480 },
  })
```

`transaction()` binds geometry, minimize, maximize, Surface, and following
operations to one visual timing. `wait: true` makes the operation resolve after
the visual transition rather than after the Desktop accepts it. `raise()`,
`changeTitle()`, and `changeHeader()` do not have transaction forms.

Local capability follows the role of the receiving layer:

| Local operation | `window` | `under` / `over` | `wallpaper` / `start-menu` |
| --- | --- | --- | --- |
| Geometry, minimize, maximize, raise | Allowed | Allowed | Rejected |
| `changeTitle()` | Allowed | Rejected | Rejected |
| `changeHeader()` | Allowed | Rejected | Rejected |
| `addSurface()`, `removeSurface()` | Rejected | Allowed | Rejected |
| `follow()`, `unfollow()` | Allowed | Allowed | Allowed |

Standard windows follow their own authoritative Window by default, keeping
System changes aligned with their ordinary Desktop representation until that
representation is explicitly detached. Every other layer begins unfollowed.
`follow(window)` replaces the current authoritative target and adopts only the
properties permitted by the receiving layer. `unfollow()` detaches while
preserving the current local state.

Local overrides do not implicitly break following. Later authoritative events
update only the property they carry. Under and over layers do not follow a
target's title or header state, and no follower copies the target's layer or
Surface.
