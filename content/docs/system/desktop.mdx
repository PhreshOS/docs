A Desktop is one complete graphical representation of the System. It provides
the workspace through which a person reaches Programs, combines System
Appearance with Desktop preferences, reports the available viewport, and
belongs to the browser Connection carrying it. Its shell includes regions such
as the wallpaper, taskbar, and Start Menu alongside the Client Endpoints it
presents.

## Desktop state

Client code uses the separate `desktop` root for state belonging to the
containing Desktop:

```ts
import { desktop } from "@phreshos/client"

const { size } = await desktop.viewport.snapshot()
const preferences = await desktop.preferences.snapshot()
const connection = await desktop.connection()
```

`desktop.viewport` exposes the current workspace size in CSS pixels and emits
a complete `{ size }` snapshot when it changes.

`desktop.preferences` exposes the effective theme, animation choice, and scale
for this Desktop. Scale is a multiplier between `0.5` and `2`, defaulting to
`1`. A preference update may set `theme`, `animations`, or `scale` to
`"default"` to restore its native or System default.

```ts
await desktop.preferences.update({ theme: "dark" })
```

`desktop.connection()` returns the browser Connection carrying this Desktop.
The executing Program needs `desktopConnection` or `connections` to access it.

## Client Windows

The System owns each Client Endpoint's authoritative Window state. A Desktop
applies the parts of that state that have meaning in the Window's current layer
and owns the measurements, pointer interaction, iframe, and animation required
to present it on one screen.

This creates two related capabilities:

- `window` records authoritative state for the Client Endpoint.
- `presentation` controls and observes how the executing Client is represented
  by its current Desktop.

They normally remain aligned, but they are not the same state. More than one
Desktop may represent the same authoritative Window, and a presentation may be
temporarily detached from it.

Client code reaches both Window capabilities through its Context:

```ts
import { context } from "@phreshos/client"
```

### Authoritative Window

Every declared Client Endpoint has one authoritative Window, even while its
execution context is stopped. The Window belongs to the Client Endpoint and
survives its execution contexts.

```ts
await context.window.setGeometry({
  x: 120,
  y: 80,
  width: 900,
  height: 640,
})

await context.window.maximize()
await context.window.setHeader(false)
```

Window operations record authoritative values. They are therefore valid even
when the current layer does not present the affected concept. For example, a
Program may record geometry while its Client is in the wallpaper layer, then
restart the Client in the standard window layer and use that geometry there.

Stopping a Client does not reset its Window. Starting it again preserves every
stored value omitted from the new launch. An explicitly supplied launch value
replaces only its corresponding authoritative value.

The Window exposes title, header, frame, default transaction, position, size,
minimized and maximized states, front state, and layer. Position and size
accept finite pixels or relative expressions such as `"1/2"`. A bare numeric
value is always a pixel count: `1` means one pixel, while `"1/1"` and `"100%"`
mean the complete available span.
`setGeometry()` accepts `{ x, y, width, height }` and commits position and size
atomically. Minimized and maximized are independent, and neither discards the
stored geometry. `raise()` brings a Window to the front of its own layer.

Window events are `move`, `resize`, `minimize`, `maximize`, `changeTitle`,
`changeHeader`, `changeFrame`, `changeTransaction`, and `front`. An atomic
geometry change emits `move` and `resize` only for the parts that changed,
after the complete geometry has been committed.

### Presentation

`context.presentation` addresses the executing Client's actual representation
on the current Desktop. A presentation change is local to that Desktop and
does not mutate the authoritative Window. Whether it may be changed directly
depends on the layer.

The standard `window` layer is permanently followed. Its presentation remains
readable and observable, but every direct presentation mutation and
`unfollow()` reject. Standard windows are controlled through `window`; the
Desktop applies those authoritative changes to the presentation. The Desktop
also enforces a minimum presented size of 260 by 160 logical pixels, limited by
the available workspace, without rewriting smaller authoritative geometry.

`under` and `over` may follow, unfollow, and accept direct presentation
mutations. `follow()` projects the applicable authoritative values, while
`unfollow()` preserves the current applied state and stops later projection:

```ts
await context.presentation.unfollow()
await context.presentation.setGeometry({
  x: 24,
  y: 24,
  width: 720,
  height: 480,
})
await context.presentation.follow()
```

`wallpaper` and `start-menu` remain permanently unfollowed:
`follow()` rejects and `unfollow()` is already satisfied.

Presentation reads and mutations describe actual application. They reject when
the current layer has no corresponding concept. Presentation event observation
is asynchronous, so unsupported events remain silent instead. Supported events
are emitted immediately as the presentation changes, including continuously
during an animated change.

The `under` and `over` layers support presentation transactions. Their
authoritative Window transaction is the default for the first appearance and
for later presentation mutations:

```ts
await context.presentation
  .transactionAndWait({ duration: 180, easing: "ease-out" })
  .setGeometry({
    x: 24,
    y: 24,
    width: 720,
    height: 480,
  })
```

`transaction()` resolves when the Desktop accepts the operation.
`transactionAndWait()` resolves after its visual transition finishes. On a
presentation operation, `true` uses the authoritative Window transaction and
`false` applies no transition. A number supplies a duration in milliseconds
using the Appearance easing, and an object supplies both duration and easing.
If the authoritative Window transaction is itself `true`, it resolves to the
Appearance transaction. Window presentation transactions are unrestricted by
the Appearance customization duration limit.

### Layers

A layer gives a Window a presentation role. The authoritative Window retains
the complete state in every layer; the Desktop decides which values can be
applied by that role.

| Layer | Presented values | Direct presentation mutation | Following |
| --- | --- | --- | --- |
| `window` | Title, header, frame, geometry, minimize, maximize, front, layer | Rejected | Required |
| `under` | Frame, geometry, minimize, maximize, front, layer | Allowed | Optional; initially unfollowed |
| `over` | Frame, geometry, minimize, maximize, front, layer | Allowed | Optional; initially unfollowed |
| `wallpaper` | Layer | Rejected | Forbidden |
| `start-menu` | Layer | Rejected | Forbidden |

The standard `window` layer has a permanent Desktop-controlled frame. Its
header defaults to visible and may be hidden independently. Programs cannot
customize or remove that frame through presentation operations.

Only the standard `window` layer presents a title because it is the only layer
with a header concept. Hiding that header does not remove the title from the
layer's contract; it only hides the region that displays it.

`under` and `over` have no header. Their frame defaults to absent and may be
enabled or customized. A frame accepts `true`, `false`, or an object with
specific `radius`, `color`, and `material` overrides:

```ts
await context.window.setFrame({
  radius: "full",
  color: "primary",
  material: { opacity: 0.8, grain: 0.03 },
})
```

An `under` or `over` launch may also set `transaction`. It controls the
Client's first appearance after the Desktop is already running and remains the
default for later presentation operations. Existing Windows do not replay
that appearance when a Desktop loads.

`wallpaper` and `start-menu` are fixed, exclusive roles. Starting another
Client in the same role ends the existing occupant's Process before presenting
the replacement. Their title, geometry, visibility, frame, and header are not
presentation concepts; the Desktop owns the region itself.

Layers are isolated for ordering. Raising a Window changes its depth only
within its own layer, and the taskbar remains above every Window layer.
A Program needs the `layers` permission to launch outside the standard layer.

```sh
phresh window inspect --process main --program notes
```
