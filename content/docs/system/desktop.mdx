A Desktop is one graphical representation of authoritative System state. A live
Client owns one authoritative Window, while the Desktop owns its local visual
representation.

## Desktop contract

| Capability | Read | Change | Event |
| --- | --- | --- | --- |
| `desktop.viewport` | `snapshot()` → `{ size: { width, height } }` | — | `resize` with the complete snapshot |
| `desktop.preferences` | `snapshot()` → `{ theme, animations }` | `update(preferences)` | `change` with the complete preferences |

The Client may read both capabilities. Updating preferences requires
`desktopPreferences` or `all`.
[Appearance](/system/appearance) defines how preferences resolve visual values.

## Window state

Every Client Endpoint owns a permanent `window` handle. Its authoritative state
contains `title`, `position`, `size`, `minimized`, `maximized`, `front`, and `layer`.

| Read | Mutation | Event |
| --- | --- | --- |
| `title()` | `changeTitle(title)` | `changeTitle` with the title |
| `position()` | `move(position)` | `move` with the position |
| `size()` | `resize(size)` | `resize` with the size |
| position and size | `setGeometry(geometry)` | `geometry` with both values |
| `minimized()` | `minimize(minimized?)` | `minimize` with the state |
| `maximized()` | `maximize(maximized?)` | `maximize` with the state |
| `front()` | `raise()` | `front` with the state |
| `layer()` | — | — |

Calling `minimize()` or `maximize()` without a value selects `true`. `raise()` brings the
Window to the front of its own layer.

## Geometry and layers

Geometry accepts finite pixels or linear workspace-relative expressions such
as `"1/2"`, `"50%"`, or `"50% + 10"`. `setGeometry()` commits position and
size atomically.

Presentation has one precedence order: minimized, maximized, then geometry.
A minimized Window is hidden. Otherwise, a maximized Window fills its Desktop
workspace; otherwise its stored geometry is displayed. Each Desktop resolves
the workspace bounds locally.

Both flags are independent. Maximizing never overwrites geometry, and restoring
visibility never clears maximization. Geometry and maximization changes remain
stored and observable while minimized. Clearing maximization reveals the current
stored geometry, so restoration requires no separate saved rectangle.

Numbers are absolute pixels. Percentages and fractions are relative values;
addition and subtraction combine terms, while multiplication and division
scale the preceding term. Other strings are rejected.

Windows occupy `wallpaper`, `under`, `window`, or `over`, from back to front.
The taskbar remains above them.

The `wallpaper` layer fills the Desktop's wallpaper area without window chrome.
The System permits one running Client Endpoint in this layer at a time. A
new launch terminates the entire Process occupying the layer before starting
the replacement. This applies to both Process creation and starting a Client
Endpoint in an existing Process.

While that Client runs, Desktop displays it instead of the Appearance wallpaper.
When it stops, Desktop returns to the Appearance wallpaper. The wallpaper role
stays visible and fills its area regardless of authoritative geometry,
minimization, maximization, or depth. Those Window values remain readable,
mutable, and observable; they do not control this role's presentation.

## Local Window

`Window` is authoritative. `context.localWindow` is this Desktop's physical
representation of that Window:

| Operation | Effect |
| --- | --- |
| `addSurface()` | Add the host Surface |
| `removeSurface()` | Remove the host Surface |
| `move(position)` | Move only the local representation |
| `resize(size)` | Resize only the local representation |
| `setGeometry(geometry)` | Change local position and size together |
| `minimize(minimized?)` | Minimize or restore only the local representation |
| `maximize(maximized?)` | Maximize or restore only the local representation |
| `changeTitle(title)` | Change only the local title |
| `follow(window)` | Follow the supplied permitted authoritative Window |
| `unfollow()` | Stop following and retain the current local state |
| `raise()` | Bring the representation to the front of its current layer |
| `transaction(transaction)` | Bind Surface, geometry, minimize, maximize, and follow operations to visual timing |

`AppearanceTransaction` requires both `duration` and `easing`. It is the same
contract as `appearance.transaction`. `WaitedTransaction` adds `wait: true`;
that form makes the requested operation resolve after visual completion rather
than after the Desktop accepts it. Easing accepts the standard CSS names or a
four-number cubic Bézier tuple.

Local operations return `Promise<void>`, have no reads or events, and change
only the current Desktop representation. Each layer accepts the operations for
properties that Desktop owns in that role; other local operations reject:

| Local operation | `window` | `under` / `over` | `wallpaper` |
| --- | --- | --- | --- |
| Geometry, minimize, maximize, raise | Allowed | Allowed | Rejected |
| `changeTitle()` | Allowed | Rejected | Rejected |
| `addSurface()`, `removeSurface()` | Rejected | Allowed | Rejected |
| `follow()`, `unfollow()` | Allowed | Allowed | Allowed |

Standard windows initially follow their own authoritative Window. Under and
over windows start with authoritative geometry and visibility but remain
unfollowed. Wallpaper also starts unfollowed, using its fixed Desktop role.
`follow(window)` tracks the properties its receiving layer permits and replaces
any previous target. `unfollow()` preserves the current local state. A stopped
target ends following without restoring an older rectangle.

Local operations do not implicitly unfollow. Subsequent authoritative changes
update only the properties that changed; a title change does not reset a local
position override. Following does not copy the target's layer or Surface.
Under and over followers do not copy titles. A wallpaper follower accepts the
relationship without adopting geometry, title, visibility, or ordering changes.

Pointer gestures, measurements, snap previews, iframe references, and animation
state remain local. Desktop gestures explicitly commit authoritative changes.
`raise()` and `changeTitle()` have no transaction form; the remaining local
operations accept visual timing through `transaction()`.
