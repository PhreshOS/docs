A Desktop is one graphical representation of authoritative System state. A live
Client owns one authoritative Window, and the Desktop owns its local visual
representation.

## Desktop contract

| Capability | Contract |
| --- | --- |
| `desktop.surface` | Read the Desktop size and observe future resizes |
| `desktop.preferences` | Read and update the effective theme and animation preference |

The Client may read both capabilities. Updating preferences requires the
`all` permission. [Appearance](/system/appearance) defines how those preferences
resolve visual values.

## Window

Window state includes title, position, size, minimized state, front state,
layer, and Client location. Geometry can use finite pixels or linear
workspace-relative expressions such as `"1/2"`, `"50%"`, or `"50% + 10"`.

## Geometry

- `move()` changes position.
- `resize()` changes size.
- `setGeometry()` commits position and size atomically.

Filling the workspace is geometry, not a separate maximized domain state. The
interface that offers restoration owns the temporary geometry to restore.

## Layers

Windows use three layers:

1. `under`
2. `window`
3. `over`

Wallpaper is Appearance rather than another Window layer. The taskbar remains
above all layers.

## Local representation

`Window` is authoritative. `LocalWindow` is one Desktop's representation.
Pointer gestures, measurements, snap previews, iframe references, and animation
state are local to that Desktop.

`context.localWindow` can add or remove the host Surface, change local geometry,
or bind those operations to one visual transaction. These operations do not
publish authoritative Window events and are accepted only for Windows in the
`under` or `over` layer.

Dragging and resizing remain local while continuous and commit as one System
request. Interaction waits for authoritative facts rather than arbitrary
animation delays.
