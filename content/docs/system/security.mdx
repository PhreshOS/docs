Security begins with one System owner and structural authority boundaries.
Initial setup registers the owner and closes registration; later Desktop
sessions authenticate as that owner.

The System provides no independent recovery authority above the owner's chosen
authentication method.

## Client authority

A Client can access its own Program, that Program's Processes and resources,
Services belonging to that Program, read-only Appearance, Desktop viewport and
preferences, and its Context capabilities. It cannot enlarge authority by
fabricating an identity or message. An inaccessible handle behaves like a
nonexistent one; a hidden sender or destination is represented as `null`.

## Permissions

Permissions come from the closed Core catalog. A Program cannot invent a
permission name or a value outside that permission's value domain.

Initial values may be declared under `client.permissions`. Installation copies
that declaration into the Program's `storage/permissions.json`, overwriting any
previous permission file. From that point onward, the file is the only source
of truth. The declaration is not a second live grant and reinstalling resets
owner changes to the newly installed declaration.

The current catalog is:

| Permission | Values | Default | Authority |
| --- | --- | --- | --- |
| `services` | Program identities | `[]` | Services belonging to every Program, or only the listed Programs |
| `programs` | Program identities | `[]` | Every Program, or only the listed Programs, including their Processes, Endpoints, Windows, resources, and Services |
| `network` | Network scopes | `[]` | Every System request target, or only targets covered by the listed scopes |
| `storage` | Storage scopes | `[]` | Every native path and operation, or selected operation-and-path scopes |
| `uploads` | None | `[]` | Create values in the public uploads collection |
| `appearance` | None | `[]` | Update System Appearance |
| `desktopPreferences` | None | `[]` | Update Desktop preferences |
| `all` | None | `[]` | Fallback authority for every permission without an exact assignment, plus unrestricted Client capabilities |

For `services` and `programs`, an empty list means every Program; a non-empty
list is an unordered set of selected Program identities. A `programs`
assignment supplies Service access for the same Programs only when `services`
has no explicit assignment. Creating or force-creating
a Program and forking a Program require the unrestricted `programs: []` grant.

For `network`, an empty list means every request target. A non-empty list contains
canonical scopes used only by `system.network.fetch()` and `system.network.websocket()`:

```ts
permissions: {
  network: [
    "https://api.example.com",
    "https://*.example.com/v1/**",
    "http://localhost:*",
    "wss://events.example.com/**",
  ],
}
```

Schemes are explicit. `*.` replaces complete leading hostname labels, `:*`
selects every port, and a final `/**` selects a path subtree. A scope without a
path selects its entire origin. Query strings and fragments do not define
authority. Broader stored scopes satisfy narrower checks. This permission
does not govern browser-native networking APIs and never requires an iframe
reload. A change governs later System operations; it does not revoke a
`Response` or `WebSocket` already returned to the Client.

For `storage`, an empty list grants every operation over the native filesystem.
A non-empty list combines an operation set with an exact path or a path subtree:

```ts
permissions: {
  storage: [
    "Documents/report.json",
    "read:Documents/**",
    "read,write:Downloads/**",
    "delete:/var/shared/temporary/**",
  ],
}
```

A path without an operation prefix grants `read`, `write`, and `delete`.
There is no `all:` prefix. Operations may be combined with commas and are
treated as an unordered set. A final `/**` includes the named path and its descendants.
Relative paths begin at `system.storage.path()`; absolute paths retain their
native meaning.

Every `path()` operation on `system.storage`, Program `data`, Program `cache`,
and System `uploads` needs a scope covering the returned native path under any
granted operation. `navigate()` and `file()` only select locations and perform
no access. Native reads, metadata, listing, space, and watching require `read`;
directory creation, file writing, and appending require `write`; deleting and
clearing require `delete`. Storage grants do not require an iframe reload and
affect only later operations.

Value-less permissions use an empty list only as their canonical present value.
For example:

```ts
permissions: {
  services: ["web-browser"],
  appearance: true,
}
```

`true` is assignment and request shorthand for the permission's default value.
It therefore selects every Program for `services` and `programs`, every request
target for `network`, every native path and operation for `storage`, and the
canonical present value for value-less permissions such as `uploads`.

When present, `all` supplies every otherwise-unassigned System capability,
uniquely permits `program.permissions`, and adds `allow-same-origin` to the
Client iframe. An explicit assignment for a permission takes priority over
`all`; this is what allows a later approved request to restrict one capability.

`context.permissions.get()` returns the exact stored assignment.
`context.permissions.allows()` checks the current stored authority without
prompting or changing it. Exact assignments take priority, then `programs` may
supply an unassigned `services` permission, and finally `all` may supply any
other unassigned permission.
`context.permissions.request()` returns only the permission: the requested
canonical list when granted, `false` when denied, or `null` when unresolved.
Every request asks the owner, including a request narrower than current
authority. Approval replaces that exact stored permission and returns it;
denial or dismissal leaves storage unchanged. Requests wait for up to two
minutes by default, and `timeout()` selects another deadline.

| Context operation | Result |
| --- | --- |
| `get(name)` | Stored `string[]`, `false`, or `null` |
| `allows(name, value?)` | Whether current stored authority covers the requested value |
| `request(name, value?)` | Requested canonical list, `false`, or `null` |
| `timeout(milliseconds).request(...)` | The same request with another deadline |

`program.permissions` is the authoritative permission-state capability:

| Program operation | Result |
| --- | --- |
| `get(name)` | Stored canonical value |
| `all()` | Stored values indexed by permission name |
| `allows(name, value?)` | Whether the stored Program permissions cover the requested value |
| `set(name, value)` | Completion |
| `delete(name)` | Completion |

`set()` accepts `true`, an allowed value set, or `false`; `null` belongs to
`delete()`. A permission declaration accepts only `true` or an allowed value
set and is copied only during installation. Arrays are canonicalized as
unordered sets.

`set()` and `delete()` are commands returning `Promise<void>`; failure rejects.
The System propagates resulting access changes to every Client Process of that
Program. Program permission management from a Client is itself
available only with `all`.

For example, if a Program has `programs: []` and the owner approves
`context.permissions.request("services", ["browser"])`, the System stores and
returns `services: ["browser"]`. That explicit Service assignment now restricts
Service access even though `programs` remains broad.

Asynchronous operations reject with `Execution is not permitted` when authority
is missing. Synchronous operations that cannot report failure remain silent.
