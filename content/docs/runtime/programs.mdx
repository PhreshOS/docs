A Program is software as the System knows it. It is the stable ownership root
around changing implementations and executions: installed files can be
replaced, development source can be attached temporarily, and Processes can
come and go without changing which software owns its storage, permissions, or
public identity.

Use a Program when the question is about the software as a whole. Use a
Process when the question is about one live run of it. This distinction lets a
Program own durable resources once while creating as many independent live
Processes as its work requires.

## Identity

Every Program has a kebab-case `identity`, a resolved human `name`, and a
resolved `version`. An omitted version becomes `0.0.0`. It may also declare a
description, icon, agent document, Server Endpoint, and Client Endpoint. The resolved `server` and `client` members describe what
a default Process should start and whether each Endpoint should begin as a
Service.

```ts
const program = await system.program.find("notes")

if (program) {
  console.log(program.identity, program.name, program.version)
  console.log(program.server?.start, program.client?.start)
}
```

```sh
phresh program inspect --program notes
```

`system.program.list()` returns the Programs visible to the caller.
Pass `true` to `list(true)` to include only installed Programs.
`find(identity)` returns one visible Program or `null`. Absence and
inaccessibility look the same: the handle does not exist. See
[Permissions](/system/security/permissions).

`system.program.create(source)` creates an uninstalled runtime Program from a
definition or an absolute `program.json` path. `forceCreate()` claims the same
identity for a new runtime Program while preserving installed files and
storage.

`assetId` identifies the current runtime incarnation used by Client asset
URLs. It may change when the Program is replaced; the public identity does
not.

## Processes belong to the Program

A Program is the only place from which one of its Processes is created. This
keeps execution attached to the definition, authority, storage, and defaults
that give it meaning; a Process identity alone is not enough to manufacture a
new run.

```ts
const process = await program.createProcess({
  name: "editor",
  client: true,
  options: { document: "welcome.txt" },
})

const same = await program.findProcess("editor")
console.log(same === process)
```

`processes()` returns all live Processes owned by the Program.
`firstProcess()` and `lastProcess()` select them by creation time.
`findProcess()` accepts either an identity or a Program-local name.
`exitProcesses()` ends them all and returns their identities.
`findOrCreateProcess()` and `runProcess()` are described with
[Processes](/runtime/processes).

## System-managed state

A Program owns runtime state managed by the System. This state describes how
the System should treat the software, rather than what its authored definition
requested. It is kept with the Program's storage, survives updates and
ordinary uninstallation, and is removed when that storage is purged.

`program.startup` controls whether the System creates one Process when it
boots.

```ts
await program.startup.enable({ name: "background", server: true })
await program.pin()
```

`startup.get()` returns its stored Launch or `null`. Calling `enable()` without
a Launch stores `{}`, which uses the Endpoint declaration defaults.
`startup.disable()` disables startup. `pinned()` returns a boolean; `pin()` and
`unpin()` change it. Pinning tells Desktop interfaces that they may retain the
Program as a favorite; it does not start a Process.

Permissions are also part of System-managed state. Their effective values are
described under [Permissions](/system/security/permissions). `definition()` remains the
source for author-declared metadata and defaults; it does not include this
mutable state.

## Program-owned resources

These resources survive independently from any one Process. All Processes of
the Program see the same ones.

| Resource | Meaning |
| --- | --- |
| `data` | Durable files |
| `cache` | Disposable files |
| `store` | Persistent key-value state |
| `database` | Writable SQLite |
| `logs` | Read-only captured Endpoint output with live records |
| `permissions` | Effective permission state and stored assignments |

`icon(size?)` returns a PNG at `small`, `medium`, or `large`; omission selects
`medium`. Programs without an authored icon receive the System default.
`agent()` returns the Program's agent document, or `null`. `hasAgent` reports
whether one is declared. `definition()` returns the complete canonical
`ProgramDefinition` accepted by `system.program.create()`; it describes the
Program and does not include mutable runtime state.

See [Storage](/system/storage), [Logs](/system/logs), and
[Permissions](/system/security/permissions).

## Installation and runtime form

An installed Program runs from files owned by the System and can be restored
after a restart. An attached Program runs directly from a project and remains
tied to the connection that introduced it. Both are the same Program domain;
their file ownership and lifetime differ.

```ts
for await (const chunk of program.install({
  launch: { name: "main", client: true },
  purge: true,
})) {
  console.log(chunk.stream, chunk.text)
}
```

```sh
phresh install
phresh install notes --run
```

`install()` and `uninstall()` are async generators because their commands can
produce ordered `stdout` and `stderr` chunks.

Installation keeps existing Processes alive while the installation command
runs. Immediately before the Program switches to its installed definition,
those Processes end. After installation succeeds, at most one Process is
created: `install({ launch })` overrides the definition's `installLaunch`.
`false` disables it, `true` uses Endpoint defaults, and a Launch supplies its
settings. Omission uses `installLaunch`; when both are absent, nothing starts.
Startup is independent and runs only when the System boots.

For installation, `purge: true` removes previous installed storage before the
new definition is applied. Uninstallation removes the installed form. With
`purge: true`, it also ends Processes, removes storage, and forgets the
runtime Program. Ordinary uninstallation of a Program that already has no
installed form completes without output. An explicit purge still removes the
remaining runtime Program and storage.

`forget()` ends live Processes and removes the runtime Program without
uninstalling its files.

## Lifecycle

A Program emits `processCreate` and `processExit` for its own Processes,
`pinned` when its pinned state changes, `uninstall` with `{ purge }` when its
installed form is removed, `permissions` with the complete effective permission
snapshot after it changes, and `forget` when the runtime Program leaves the
registry. The System-level Program collection publishes `create`, `install`,
`uninstall`, `forget`, `{ program, pinned }`, and `{ program, permissions }`
changes for visible Programs.
