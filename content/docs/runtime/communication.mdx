PhreshOS communication lets Endpoints exchange application values without
making browser frames, worker channels, processes, or network transports part
of the application contract. The operation is chosen by intent; the handle is
chosen by position:

| Position | Meaning |
| --- | --- |
| `context` | the Endpoint incarnation currently executing |
| `endpoint` | one exact Process role across its starts and stops |
| `service` | whichever ready Endpoint currently occupies a stable public address |

All three expose the same publication and observation language where that
meaning is available.

## Publishing a value

`publish(event, payload?)` is synchronous and fire-and-forget. Use it for a
fact or signal whose sender does not require one correlated result. It reports
no delivery result. If its destination is unavailable, the publication is not
delivered.

```ts
context.subscribe("document.changed", message => {
  console.log(message.from, message.payload)
})

context.publish("client.ready")
```

Context receives messages as `{ from, payload }`. Traffic originating from an
Endpoint is observed as `{ to, payload }`. An identity outside the observer's
authority is `null`.

`context.publish()` produces output from the executing Endpoint without a
destination. `endpoint.publish()` targets that exact Endpoint.
`service.publish()` targets the Endpoint currently occupying a Service
address.

Importing an SDK does not publish, subscribe, or begin application traffic.
The Endpoint boundary only routes registrations and values requested by SDK
operations. A Server runtime emits one boundary-owned readiness signal; all
application communication begins with an explicit publish, ask, answer,
subscription, wait, or event iterator.

## Observing future events

Every `Subscribable` offers three ways to observe the same future event
stream:

```ts
const cleanup = target.subscribe("changed", value => console.log(value))
const next = await target.wait("changed")

for await (const value of target.events("changed")) {
  console.log(value)
}
```

`subscribe()` creates a persistent registration and returns its cleanup.
`wait()` resolves once with the next matching message and uses a ten-second
deadline by default. `events()` returns a long-lived async iterator; its
optional `signal` cancels iteration, while `capacity` controls its queued
messages and defaults to `64`.

These operations observe future messages. They do not read or replay current
state because an application event is an occurrence, not a state snapshot.
When a consumer needs current state, it should first use the domain's read
operation and then follow its change events. Calling `subscribe(subscriber)`
or `events()` without an event name preserves each event as a correlated
`{ event, message }` capture.

A persistent subscription may remain registered while an Endpoint or Service
is temporarily unavailable. It ends when its cleanup is called or when the
owning boundary can prove that future delivery is impossible. An async event
iterator follows the same rule and also ends when iteration is closed or its
abort signal fires.

## Asking a Server

Questions are directed to Server Endpoints and Server Services. Unlike a
publication, `ask()` represents one correlated request whose caller requires
one success or failure answer:

```ts
const status = await server.ask("status.read")
const report = await server.timeout(30_000).ask("report.create", {
  format: "pdf",
})
```

The executing Server registers an answerer through its Context:

```ts
const cleanup = context.answer("status.read", () => ({ ready: true }))
```

The answerer receives the question payload and the asking Endpoint when that
identity is visible:

```ts
const cleanup = context.answer<
  { path: string },
  { opened: boolean }
>("document.open", async ({ payload, from }) => {
  console.log("Requester is visible", from !== null)
  return { opened: await openDocument(payload.path) }
})
```

Returning resolves the ask. Throwing or rejecting sends a failed answer, and
the asker's Promise rejects with that failure. The returned cleanup removes
only this answer registration.

An ask rejects when its destination is unavailable or disappears before
answering. Once delivered, an unanswered question waits until its deadline.

The default deadline is ten seconds and is shared with any readiness wait for
that target.

`endpoint.traffic` observes directed communication originating from one
Endpoint. Ordinary publications retain their event name and carry
`{ to, payload }`. `subscribeAsks()` and `asks()` expose questions as
`{ event, questionId, message: { to, payload } }`. A Server traffic surface
also exposes `subscribeAnswers()` and `answers()`, whose message contains the
correlated success or failure outcome. Traffic observation does not consume or
alter delivery.

## Values across the boundary

Payloads are not restricted to JSON. Communication preserves `undefined`,
`bigint`, `Date`, `Map`, `Set`, `RegExp`, `URL`, `Error`, and binary data
alongside JSON-compatible values. An `ArrayBuffer` or typed-array view
arrives as a `Uint8Array`. Functions and symbols arrive as `null`.

This value contract is the same across Client, Server, and Node.
