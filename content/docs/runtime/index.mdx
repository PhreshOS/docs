The runtime separates four questions that ordinary applications often combine:

- **Program** — What software exists, and which durable resources and policy
  belong to it?
- **Process** — Which live run of that software are we talking about?
- **Endpoint** — Which execution role inside that run is being addressed?
- **Service** — How can other software reach that Endpoint without owning its
  Process?

These are separate domains because their lifetimes differ. A Program can
remain installed with no live Processes. A Process can keep running while one
of its Endpoint execution contexts is stopped. An Endpoint handle remains
stable across those starts and stops. A Service address can remain known while
its provider is temporarily unavailable.

A Program is the stable root. It can own multiple live Processes. Every
Process has one permanent Server Endpoint and one permanent Client Endpoint.

```text
Program
└── Process
    ├── Server Endpoint
    └── Client Endpoint
```

A Service is the discoverable form of a named Process Endpoint, not another
execution object beside it. The Process still owns the Endpoint and its
lifecycle; the Service gives callers a stable address without granting them
control of that Process.

You meet these objects through `system` in Client, Server, Node, and the CLI.
The environment changes how the call reaches the System. A Program's Client
and Server Endpoints share its permission state, while Node and the CLI use an
owner-local connection. None of this changes what the objects mean.

```ts
const program = await system.program.find("notes")
const process = program && await program.createProcess({ client: true })
```

```sh
phresh program inspect --program notes
phresh process create --program notes --client
```

Within one SDK context, reaching the same entity again returns the same
handle.
