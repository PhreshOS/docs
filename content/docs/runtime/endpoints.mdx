Every Process owns one permanent `ServerEndpoint` handle and one permanent
`ClientEndpoint` handle. Both implement the shared Endpoint contract; each adds
only capabilities inherent to its execution role.

## Shared contract

| Member | Contract |
| --- | --- |
| `traffic` | Directed publications and questions originating here |
| `lifecycle` | `start` and `stop` transitions at this permanent address |
| `process()` | Owning Process |
| `exists()` | Whether a current incarnation exists |
| `waitReady(timeout?)` | Wait for a usable incarnation; ten seconds by default |
| `start()` | Start a fresh incarnation |
| `stop()` | Stop the incarnation without implicitly ending the Process |
| `isService()` | Whether the current incarnation is a Service |

Endpoints also implement `publish()`, `subscribe()`, `waitFor()`, and `events()`
for application communication. These operations remain on the Endpoint root;
only lifecycle transitions use `endpoint.lifecycle`.

Starting rejects when the Process is gone, the Program did not declare that
Endpoint, or an incarnation is already starting or live. Stopping rejects when
the Endpoint is absent or stopping, or when it would remove the Process's final
live Endpoint.

A Client is ready when it exists. A Server must also announce readiness.
Temporary absence remains waitable while the Process exists; readiness rejects
when that Process can no longer provide a future incarnation.

## Events

| Surface | Events |
| --- | --- |
| Endpoint root | Application-defined publications |
| `lifecycle` | `start: undefined`, `stop: undefined` |
| `traffic` | Directed application events and outgoing questions |
| Server `traffic` | Directed application events, questions, and answers |

Lifecycle events exist because a permanent Endpoint handle may observe
multiple incarnations. A Process does not emit separate Endpoint start and stop
events.

## Server Endpoint

`ServerEndpoint` adds `ask(event, payload?)` and `timeout(milliseconds)` because
questions are addressed to Servers. `start(serverLaunch?)` may select the
Service role for the new incarnation.

A Server executes host-side JavaScript in one of two declared modes:

<Tabs items={["Command", "Worker"]}>
  <Tab value="Command">
    `startCommand` starts and supervises an operating-system process tree.
  </Tab>
  <Tab value="Worker">
    `entryFile` loads an ECMAScript module as a Worker owned by the System.
  </Tab>
</Tabs>

Both modes expose the same Server SDK contract. A Worker is not a security
boundary and does not have an independent working directory.

## Client Endpoint

`ClientEndpoint` adds its permanent `window` capability.
`start(clientLaunch?)` may select the Service role and initial Window title,
size, position, layer, location, and minimized state.

A Client executes in a Desktop iframe. It may access its own Program, that
Program's Processes and Services, and its Context and Desktop capabilities.
Foreign Programs, Services, and mutable visual state require their applicable
permissions; see [Security](/system/security).

The iframe permits scripts and forms. With effective `all`, it also permits
same-origin access. Moving between those sandbox states requires a reload.

## Client assets

The browser always loads `/program/<assetId>/assets/`. In production the System
serves installed Client files. During development it proxies the declared
HTTP(S) Client server, including WebSocket traffic, through the same address.
Installation still requires Client files that the System can copy into
installed storage.
