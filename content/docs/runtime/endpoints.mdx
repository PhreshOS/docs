An Endpoint is one permanent execution role inside a Process. The handle names
the role; a running execution context is one temporary incarnation performing
that role. Keeping those concepts separate lets callers subscribe, wait, and
address the Endpoint before it starts and across later restarts.

Every Process therefore exposes both Server and Client Endpoint handles. The
handle itself carries no initial execution data and does not claim that the
Program declared or started that role. Operations that need a declared or live
Endpoint validate that condition when they run.

`running()` reports whether the Endpoint currently has an execution context.
`endpoint.lifecycle` publishes `start` and `stop` whenever that context
changes.

## Shared behavior

Both Endpoint kinds can publish application events, observe messages, inspect
their outgoing traffic, find their owning Process, and report whether their
current execution context is a Service.

```ts
const client = process.client

client.lifecycle.subscribe("start", () => console.log("Client started"))

await client.start()
await client.waitReady()
```

`process()` returns the owning Process. `subscribe()`, `wait()`, and
`events()` observe application publications addressed to this Endpoint;
`publish()` sends a publication to it. Lifecycle observation is intentionally
separate under `endpoint.lifecycle`, so application event names cannot collide
with `start` or `stop`.

`waitReady()` waits for an execution context that can be used. A Client is
ready when it is running. A Server must also announce readiness after its SDK
can receive IPC traffic; until then there is no Server answer registration to
retain incoming questions, so sending them would lose work. The default
deadline is ten seconds. Temporary absence remains waitable while the owning
Process exists.

Readiness is current state, not a consumed event. Two concurrent
`waitReady()` calls waiting on the same incarnation resolve together. A later
call resolves immediately while the Endpoint remains ready and waits again
after it stops.

`start()` ensures that an execution context is running. If one already exists, the
call resolves without replacing it or publishing another lifecycle event;
launch values configure a context only when one must be created.
`stop()` resolves when the execution context is already absent. Every
Promise-based operation through the Endpoint handle rejects when the Process
has ended or the Program never declared that Endpoint kind. Stopping rejects if it would remove the
Process's final live Endpoint. Stopping never exits the Process.

## Server Endpoint

The Server Endpoint runs host-side code and answers questions.
`ask(event, payload?)` sends a question to the current Server execution context.
`timeout(milliseconds)` selects another deadline.

`ask()` first waits for the current Server incarnation to become ready, then
sends the question. If that incarnation stops first, the operation rejects
rather than silently moving the question to a later run. The same deadline
covers readiness and the answer.

```ts
const health = await process.server.ask("health.read")
```

A Server declaration chooses one execution mechanism: a supervised operating
system command, an ECMAScript module loaded in a Node.js Worker, or a bundled
module loaded in a capability-contained Sandbox. These mechanisms have the
same Server SDK and Endpoint contract. They differ in the host authority
available outside the System API. See [Endpoint Execution](/system/security/execution).

`server.start({ service: true })` may override the Service role for that new
execution context.

## Client Endpoint

The Client Endpoint owns a permanent authoritative `window` value. Each
running execution context presents through a Desktop iframe. The Client
declaration's `sandbox` value determines how that document executes: omission
uses a sandboxed iframe, while `false` removes the sandbox attribute.

A Client may be represented by more than one Desktop context. Publications
and future events can be observed across those contexts, but a question would
not identify one unambiguous Client answerer. For that reason Clients receive
publications while the request-and-answer contract belongs to Servers.

Its launch can choose the Service role and the initial title, header
state, size, position, layer, minimized state, and maximized state.

```ts
await process.client.start({
  title: "Inspector",
  layer: "over",
  size: { width: 520, height: 420 },
})
```

The iframe loads `/program/<assetId>/assets/`. In production, that address
serves installed Client files. During development, the System proxies the
declared Client development server through the same address, including its
WebSocket traffic.

See [Desktop](/system/desktop) for Windows.

## Traffic

`endpoint.traffic` observes communication originating from that Endpoint.
Publications appear as `{ to, payload }`. Questions appear through
`subscribeAsks()` and `asks()`. A Server's traffic can additionally observe
answers through `subscribeAnswers()` and `answers()`. An identity outside the
observer's authority is `null`.

Ask and answer captures contain the application event and a `questionId` that
correlates the pair. An answer outcome is either a successful `result` or a
failed error string. Traffic subscriptions are observation only: they neither
consume the value nor affect delivery to the destination.
