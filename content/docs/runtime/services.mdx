A Service is an Endpoint that has chosen to be discoverable while it is
running. It lets another Program communicate with that Endpoint without owning
its Process or controlling its lifecycle.

Every Service address has three coordinates:

```ts
type ServiceAddress = {
  program: string
  process: string
  endpoint: "server" | "client"
}
```

`program` is the stable Program identity. `process` is the Program-local
Process name and acts as the Service name. `endpoint` identifies the Server or
Client Endpoint. An unnamed Process cannot be a discoverable Service.

## Discovering Services

`system.service.list()` returns every Service currently available to the
caller. `search(name)` narrows that result to Services whose Process has the
given name. More than one Program may use the same Process name, so a search
can return several Services. For example, separate text-editing and
image-editing Programs may both expose a Process named `editor`.

```ts
const editors = await system.service.search("editor")

for (const editor of editors) {
  console.log(editor.address())
}
```

Only ready Endpoints running in Service mode appear in discovery results.
Results are also limited by the caller's `services` permission.

## Preparing an exact address

When the address is already known, `prepare()` creates its canonical local
handle without contacting the System:

```ts
const editor = system.service.prepare({
  program: "text-studio",
  process: "editor",
  endpoint: "server",
})
```

The Endpoint discriminant determines whether the result is a `ServerService`
or `ClientService`. Repeated preparation of the same address in one SDK
context returns the same handle.

Preparing a handle does not prove that the Service exists, is available, or is
authorized. Those facts matter when an asynchronous operation is performed.
`available()` checks the current state, while `waitReady()` waits for an
available Endpoint at that address.

```ts
await editor.waitReady()
const result = await editor.ask("document.open", { path: "welcome.txt" })
```

The address is stable across execution contexts. If the matching Endpoint
stops, the handle becomes unavailable rather than ending. If a Process with
the same Program identity and Process name later exposes the same Endpoint as
a ready Service, that handle becomes usable again.

## Program metadata

An available Service exposes the current provider Program's presentation
metadata as one consistent snapshot:

```ts
const metadata = await editor.programMetadata({ icon: "small" })

console.log(metadata.name, metadata.version)
document.querySelector("img")!.src = URL.createObjectURL(metadata.icon)
```

The optional `icon` value is `small`, `medium`, or `large`; omitting the options
object or `icon` selects `medium`. This operation uses Service authority rather
than exposing a Program handle. It rejects when the Service is unavailable,
and its result is not retained by the Service after the Endpoint stops.

## Availability and communication

A Service handle publishes `available` and `unavailable` lifecycle events.
These events describe whether the addressed Endpoint can currently receive
communication; application events remain on the Service handle itself.

```ts
editor.lifecycle.subscribe("unavailable", () => {
  console.log("The editor is temporarily unavailable")
})

editor.subscribe("document.changed", change => {
  console.log(change)
})
```

Services expose publishing and event observation. Server Services additionally
support `ask()` and `timeout().ask()`. They do not start or stop their Endpoint;
those operations remain with the Endpoint and Process owners.

## Becoming discoverable

An Endpoint declaration can select Service mode by default, and a Launch can
select it for one execution context:

```ts
const process = await program.createProcess({
  name: "editor",
  server: { service: true },
  client: false,
})
```

A Service is available only while that named Process has a ready Endpoint
running in Service mode. `endpoint.isService()` and `context.isService()`
report the resolved role of the current execution context.

Service authority is independent of Program authority. Granting
`services: ["editor"]` permits access to every available Service whose Process
is named `editor`, across Programs and Endpoint kinds. It does not make those
Programs visible, and the `programs` permission does not grant access to their
Services. See [Permissions](/system/permissions).
